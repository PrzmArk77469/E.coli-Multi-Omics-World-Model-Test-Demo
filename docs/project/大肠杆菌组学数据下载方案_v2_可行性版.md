# 大肠杆菌多组学数据下载方案 v2（可行版）

> 版本：v2.0  
> 日期：2026-09-14  
> 定位：建设可持续更新的 E. coli 多组学数据湖，而不是执行一次不可控的全量 raw data 镜像。  
> 核心结论：元数据全量、核心证据集选择性下载、全物种原始数据按需回源。

## 0. 决策摘要

### 0.1 推荐的总体形态

项目最终应形成四层体系：

| 层级 | 覆盖目标 | 保留策略 | 建议数据量 |
|---|---|---|---|
| L0 元数据目录 | E. coli 全部可发现 study/sample/run/file | 全量、长期、append-only | 10-100 GB |
| L1 核心证据湖 | MG1655 及少数关键菌株的高质量 raw + processed 数据 | 选择后长期保留 | 约 2-8 TiB |
| L2 泛基因组目录 | 全物种 assembly、注释、菌株谱系 | 完整 assembly，raw WGS 默认不保存 | 数百 GB 至数 TiB |
| L3 按需回源层 | 全物种 WGS 及其他低频 raw 数据 | 只在具体分析需要时下载 | 不设常驻镜像 |

### 0.2 明确不做的事情

- 不把 ENA `tax_tree(562)` 对应的约 228.5 TiB FASTQ 一次性全部下载。
- 不把 WGS raw reads 当作全物种 genomics 的默认存储形式。
- 不把 GEO、PRIDE、MetaboLights 等来源的 processed matrix 默认为可直接合并的数据。
- 不把 EcoCyc、KEGG、BRENDA 等许可受限知识库与 NCBI/ENA 开放数据放在同一许可层。
- 不在第一版建立全菌株、全条件、真正 matched 的“完整多组学矩阵”。
- 不使用单一关键词搜索声称“已经找全”。完整性必须由来源注册表、查询式和快照日期定义。

### 0.3 可行性判断

| 目标 | 判断 | 条件 |
|---|---|---|
| 全库 accession 与元数据发现 | 高可行 | 多来源适配器、限速、快照和去重 |
| MG1655 核心多组学证据集 | 可行 | 只选择高质量、条件完整、许可明确的数据 |
| 全物种 assembly 与泛基因组 | 可行 | 优先 NCBI dehydrated package，不做全 WGS raw 镜像 |
| 全物种 raw FASTQ 长期镜像 | 技术上可行，工程上不推荐 | 需独立存储预算和长期传输计划 |
| 真正 matched 的跨组学样本 | 部分可行 | 必须按 A/B/C 分层，不能把条件匹配当作同样本 |

## 1. 范围定义

### 1.1 生物范围

#### 核心集

- E. coli K-12 MG1655
- 参考基因组：`GCF_000005845.2`
- 参考序列：`NC_000913.3`
- MG1655 TaxID：`511145`
- 后续按实际需求加入 BW25113、W3110、BL21/B 系等。

#### 扩展菌株集

- REL606
- O157:H7
- CFT073
- 常用实验室株、致病型代表株和环境分离株

扩展菌株应按菌株单独维护，不允许直接使用 MG1655 坐标解释表达或调控数据。

#### 物种层

- E. coli species-wide：NCBI TaxID `562`
- INSDC 序列数据统一按 `tax_tree(562)` 检索。
- 对 `tax_id=562` 但没有明确 strain 的记录保留，但标记为 `strain_unresolved`。

### 1.2 数据范围

| 数据类型 | L0 元数据 | L1 核心证据 | L3 按需 raw |
|---|---:|---:|---:|
| Genome/Assembly | 全量 | MG1655 + 关键菌株 | 选定菌株 WGS |
| RNA-seq | 全量 | 高质量条件数据 | 扩展条件 |
| ChIP-seq/ChIP-exo | 全量 | 优先 | 扩展数据 |
| Ribo-seq | 全量 | 优先 | 扩展数据 |
| Tn-seq/TraDIS | 全量 | 优先 | 扩展数据 |
| Methylome | 全量 | 选定 | 扩展数据 |
| Proteomics | 全量 | 选定 raw + processed | 其他 raw |
| Metabolomics | 全量 | 选定 raw + processed | 其他 raw |
| Fluxomics | 全量 | 手工筛选 | 专题需要时 |
| Interactomics | 全量 | curated PPI + 预测层分离 | 不适用 |
| Phenomics | 全量 | 核心表型 | 扩展 |
| Knowledge base | 全量索引 | 许可允许部分 | 不适用 |

### 1.3 “全”的操作定义

本项目中的“全”只允许使用以下三种表述：

1. **全量发现**：截至明确快照日期，来源注册表中所有可程序化检索到的记录。
2. **核心完整**：满足预先定义的质量、条件和许可规则的 MG1655 数据。
3. **按需覆盖**：指定分析问题需要的数据可以稳定回源，不承诺本地常驻。

任何报告必须注明：

```text
snapshot_date
source_registry_version
query_definition
included_omics
excluded_reasons
```

## 2. 已核验的数据规模

2026-09-14 的抽样核验结果如下：

| 指标 | 当前量级 |
|---|---:|
| ENA `tax_tree(562)` read_run | 约 604,829 runs |
| ENA 唯一 study | 约 9,881 |
| ENA FASTQ 字节字段合计 | 约 228.5 TiB |
| 其中 WGS | 约 176.7 TiB |
| 排除 WGS 后 | 约 51.8 TiB |
| MG1655 相关 runs | 约 20,896 |
| MG1655 相关 FASTQ | 约 12.6 TiB |
| NCBI SRA 物种级 records | 约 630,037 |
| NCBI MG1655 SRA records | 约 20,475 |
| PRIDE E. coli 关键字项目 | 约 1,409 |

注意：

- `fastq_bytes` 合计是清单估算，不等于完整归档体积。
- 少量记录缺少 `fastq_bytes`，还存在 BAM/CRAM、vendor raw、supplementary files 等非 FASTQ 文件。
- 蛋白组、代谢组、通量组不包含在上述 228.5 TiB 内。
- 任何下载预算都必须由 L0 清单实时计算，不能直接照搬本文数字。

## 3. 数据源职责

| 数据层 | 主来源 | 辅助来源 | 本项目职责 |
|---|---|---|---|
| Genome/Assembly | NCBI Datasets | ENA | NCBI 作为 assembly 与 taxonomy 权威 |
| Raw sequencing | ENA | NCBI SRA | ENA 作为主要 FASTQ manifest 与下载通道 |
| GEO processed | GEO | BioStudies | 保存 series metadata、supplementary 和平台信息 |
| Transcription | GEO/ENA | iModulonDB/PRECISE | raw 重处理优先，作者 processed 作为对照 |
| Regulation | RegulonDB | GEO/ENA | RegulonDB 作为 regulatory knowledge 主干 |
| Proteomics | ProteomeXchange | PRIDE/MassIVE/jPOST/iProX | 统一发现，按 repository 下载 |
| Metabolomics | MetaboLights | MW/GNPS/MassIVE | metadata 与 raw/processed 分开管理 |
| Methylomics | ENA/SRA | REBASE | raw calls + motif/MTase knowledge 分层 |
| PPI | IntAct | BioGRID | experimental 与 predicted 必须分表 |
| Metabolic model | BiGG iML1515 | EcoCyc | 模型、reaction、GPR 和网络约束 |
| Knowledge scaffold | EcoCyc | UniProt/ECMDB | 受许可约束，只保留允许使用的部分 |
| Cross-source discovery | 多来源联合 | OmicsDI | OmicsDI 仅作补漏，不作唯一总目录 |

### 3.1 避免重复下载

NCBI、ENA 和 DDBJ 属于 INSDC，原则上同一份原始测序数据只选择一个执行下载源。

推荐：

```text
NCBI  : taxonomy、BioProject、BioSample、Assembly、GEO metadata
ENA   : 大批量 run manifest、FASTQ、MD5、bytes、download execution
DDBJ  : 通过 INSDC 交叉引用发现，不建立日常重复下载通道
```

### 3.2 许可分层

每个来源必须映射到唯一许可标签：

| license_tag | 含义 | 允许进入公开镜像 |
|---|---|---:|
| `open_reusable` | 明确允许复用和再分发 | 是 |
| `open_attribution` | 需要署名或遵守 study 级条款 | 按条款 |
| `download_only` | 可下载，但限制再分发 | 否 |
| `academic_only` | 仅限学术许可范围 | 否 |
| `commercial_restricted` | 商业使用或再分发受限 | 否 |
| `unknown` | 条款未确认 | 否 |

下载动作和再分发动作必须使用两个不同字段：

```text
may_download
may_redistribute
```

## 4. 数据量与存储策略

### 4.1 常驻存储

| 层 | 建议存储 | 目标 |
|---|---|---|
| L0 metadata | 对象存储 Standard + DuckDB/Parquet | 频繁查询，体积小 |
| L1 raw core | 对象存储 Standard/IA | 当前分析和重建 |
| L1 processed | 对象存储 Standard | 模型和积分任务直接读取 |
| L1 历史版本 | IA/Archive | 可恢复，不参与日常计算 |
| L2 assemblies | IA/Archive | 按需回取 |
| L3 raw | 不入常驻库 | 下载、分析、按政策删除或归档 |

### 4.2 本地临时盘

每批处理应准备：

```text
free_scratch >= 2 x selected_raw_batch_size
```

原因：

- 解压和中间 BAM/CRAM 往往大于压缩 FASTQ。
- 校验、排序、去重和参考索引需要额外空间。
- 失败重跑不应覆盖唯一副本。

### 4.3 下载时间估算

使用以下公式：

```text
time_hours = total_bytes / effective_throughput_bytes_per_second / 3600
```

参考：

- 100 MB/s：1 TiB 约 3.1 小时。
- MG1655 全量 12.6 TiB：100 MB/s 约 1.5 天。
- 物种级 228.5 TiB：100 MB/s 约 28 天，尚未计算重试、校验和处理时间。

因此，下载前必须通过 manifest 给出：

```text
selected_runs
selected_bytes
estimated_time
scratch_required
archive_required
license_blocked_bytes
```

## 8. 数据选择与评分

### 8.1 硬门槛

以下任一条件不满足，不进入自动核心集：

- 菌株无法解析到明确的参考体系。
- 文件不可访问或没有可验证的校验值。
- 许可状态为 `unknown` 或明确禁止本项目用途。
- 同一数据的重复副本，且已有更高质量来源。
- assay 类型无法可靠判断。
- raw 数据缺少 study/sample 关联。

### 8.2 选择评分

建议总分 100 分：

| 项目 | 分值 |
|---|---:|
| 样本与条件元数据完整性 | 25 |
| 菌株和参考坐标可信度 | 20 |
| assay 与平台质量 | 20 |
| 与核心问题的条件相关性 | 15 |
| 许可与可复用性 | 10 |
| raw/processed 文件完整度 | 10 |

建议阈值：

```text
>= 80  : 自动进入 L1
60-79  : 人工复核
< 60   : 仅保留 L0 元数据
```

### 8.3 多组学整合等级

```text
A 级：同一个 biological sample 包含多个 omics
B 级：同 study、同菌株、同 condition，但不同 sample
C 级：跨 study，通过菌株和条件匹配
```

所有整合结果必须保留 `integration_level`。C 级数据不得在论文或模型报告中被描述为 matched sample。

## 9. 下载系统

### 9.1 必备组件

- source adapter：每个来源独立实现，不把查询逻辑散落在下载脚本中。
- rate limiter：遵守 API 配额；NCBI 正式运行使用 API key。
- request cache：保存原始响应和查询快照。
- download queue：支持优先级、重试、断点续传和并发上限。
- checksum verifier：MD5/ETag/SHA256 按来源能力校验。
- manifest updater：文件状态和错误可审计。
- storage quota：超过阈值自动停止新下载。
- cost reporter：每日报告新增字节、传输和失败重试。

### 9.2 推荐流程

```text
1. 读取 source_registry.yaml
2. 拉取 metadata，写 query snapshot
3. 标准化 accession 与字段
4. 建立 crossref 并去重
5. 计算 omics、strain、bytes、license 统计
6. 应用硬门槛和评分
7. 生成 dry-run download plan
8. 人工批准超过阈值的批次
9. 下载到 scratch
10. 校验文件和元数据
11. 处理或归档
12. 更新 manifest 和 data card
```

### 9.3 下载工具分层

```text
元数据与 API       : Python httpx/requests + tenacity
ENA 批量 FASTQ     : enaBrowserTools / Aspera / Globus
NCBI assembly      : NCBI datasets dehydrated package
NCBI SRA           : sra-tools 或 ENA 镜像
小文件与报告       : rclone/ossutil
内部对象存储       : ossutil/rclone + checksum
```

### 9.4 第一批 dry-run 查询

ENA 元数据清单示例：

```bash
curl -G 'https://www.ebi.ac.uk/ena/portal/api/search' \
  --data-urlencode 'result=read_run' \
  --data-urlencode 'query=tax_tree(562)' \
  --data-urlencode 'fields=run_accession,study_accession,sample_accession,tax_id,scientific_name,library_strategy,library_source,fastq_bytes,read_count,base_count' \
  --data-urlencode 'format=tsv' \
  --data-urlencode 'limit=0' \
  > ecoli_ena_all_runs.tsv
```

此命令只生成清单，不下载 FASTQ。

MG1655 参考数据：

```bash
datasets download genome accession GCF_000005845.2 \
  --include genome,rna,cds,protein,gff3,gbff,seq-report \
  --filename MG1655.zip
```

## 10. 处理与标准化

### 10.1 参考体系

所有 MG1655 数据统一映射到固定版本：

```text
assembly: GCF_000005845.2
sequence: NC_000913.3
annotation snapshot: 固定并记录哈希
```

泛基因组数据不能直接使用单一坐标合并，必须使用 ortholog/pangenome gene family。

### 10.2 推荐处理原则

- raw data 永不覆盖。
- processed output 必须带 pipeline name、version、container digest 和参数。
- 样本表、参考表和 pipeline 版本必须共同进入数据版本。
- 优先重处理核心 raw 数据，作者 processed matrix 作为验证层。
- 每个 assay 独立 QC，不把统一 z-score 当作数据清洗。
- 所有 metabolite 映射到至少一个稳定标识，例如 ChEBI、InChIKey。
- protein 映射到 UniProt、gene name、locus tag，并处理多映射。
- reaction 和 GPR 使用 iML1515/EcoCyc 的明确版本。

### 10.3 建议 pipeline 家族

| 数据类型 | 处理方向 |
|---|---|
| Genome/variant | Bactopia、Snippy、BWA + 细菌专用 caller |
| Annotation | Bakta/Prokka |
| Pangenome | Panaroo/Roary |
| RNA-seq | nf-core/rnaseq 或统一 STAR/Salmon 流程 |
| ChIP-seq | nf-core/chipseq 或细菌适配流程 |
| Ribo-seq | 专用 ribosome profiling pipeline |
| Proteomics | 保存 raw/processed，统一重新搜索时固定 FASTA 和参数 |
| Metabolomics | MZmine/MS-DIAL 输出 + 统一代谢物映射 |
| Fluxomics | 保留原始 tracing 与 MFA 模型版本 |

## 11. 实施阶段

### 阶段 0：范围冻结

周期：第 1 周

交付：

```text
scope.yaml
source_registry.yaml
license_registry.parquet
core_strain_list.yaml
selection_policy.yaml
```

通过条件：

- 明确核心菌株和物种边界。
- 明确“全量发现、核心完整、按需覆盖”的定义。
- 明确禁止进入公开镜像的 source/license。

### 阶段 1：L0 元数据目录

周期：第 2-4 周

交付：

- `studies/samples/assays/files/accession_crossref`
- 各组学、菌株、数据量和 license 统计
- 去重规则与冲突报告
- 第一版 coverage report

通过条件：

- ENA/NCBI 主路径可稳定重复生成。
- PRIDE、MetaboLights、MW、RegulonDB 至少有独立 adapter 或标准导入流程。
- 每个字段知道来源、含义和更新时间。

### 阶段 2：小规模真实下载试点

周期：第 5-6 周

范围：

- 20-50 个 MG1655 assays
- 覆盖 RNA-seq、ChIP-seq、protein、metabolite 中至少三类
- raw 和 processed 各至少一条完整路径

交付：

- 下载成功率和重试报告
- checksum 验证报告
- scratch 峰值和单位样本成本
- reference/pipeline 冻结版本

通过条件：

- 任一失败任务可自动重试并续传。
- 文件可从 manifest 重建。
- 处理结果可追溯至 raw、sample、reference 和 pipeline commit。

### 阶段 3：L1 核心证据湖

周期：第 2-3 个月

目标：

- MG1655 全组学覆盖
- 每个组学选择质量最高的代表数据，不追求 raw 全收
- 形成第一版 gene/metabolite master 和 A/B/C 整合表

交付：

- `sample_matched_multiomics.parquet`
- `condition_matched_multiomics.parquet`
- 数据卡、QC 报告、许可报告

### 阶段 4：标准化与分析闭环

周期：第 3-4 个月

交付：

- RNA/protein/metabolite/flux 的标准化矩阵
- pathway、TF、reaction 和 phenotype 投影
- FBA/network baseline
- 3 组可重复扰动案例

### 阶段 5：物种级扩展

周期：第 4 个月以后

原则：

- 先扩展 assembly/pangenome。
- 再按科学问题选择 strain-specific omics。
- raw WGS 默认进入 L3，不进入 L1。

## 12. 成本与护栏

### 12.1 预算公式

```text
monthly_cost =
  object_storage_bytes_by_class
  + request_cost
  + egress_cost
  + temporary_disk_cost
  + CPU_processing_cost
  + on_demand_GPU_cost
```

下载阶段主要是 CPU 和网络 I/O，不需要长期 GPU。

### 12.2 必须设置的硬限制

| 项目 | 建议 |
|---|---:|
| 单次自动下载上限 | 500 GiB |
| 单次需审批下载 | 大于 500 GiB |
| L1 raw 常驻上限 | 8 TiB，达到 80% 告警 |
| scratch 空闲空间 | 低于批处理需求的 2 倍时停止新任务 |
| 未处理 raw 保留 | 由 selection_policy 决定 |
| 失败重试 | 有上限，避免成本失控 |
| 并发下载 | 按来源限速，不为速度关闭完整性校验 |
| GPU | 数据采集和标准化阶段默认不启用 |

### 12.3 存储升级条件

只有满足以下条件才扩大 L1：

1. 新增数据进入已定义的核心问题。
2. 样本条件字段完整度达到阈值。
3. 有对应处理 pipeline 和 QC 标准。
4. 新增数据的长期价值高于按需回源成本。
5. 存储增长不突破月度硬预算。

## 13. 验收标准

### 13.1 技术验收

- 一条命令可重建元数据快照。
- 一条命令可生成 dry-run 下载计划。
- 下载任务支持重试、续传和校验。
- 每个文件都有来源 URL、大小、校验值和下载状态。
- 任一 processed 结果可追溯到 raw、sample、reference 和 pipeline version。
- 从对象存储和 Git 完成一次全量恢复演练。

### 13.2 科学验收

- MG1655 核心组学至少覆盖 RNA、protein、metabolite，并尽量覆盖 regulation、Ribo、phenotype。
- 每个矩阵有明确单位、参考坐标和样本筛选规则。
- matched 与 condition-matched 严格区分。
- 至少完成三个可重复扰动场景。
- 结果与 FBA、RegulonDB 或公开实验趋势至少有一种独立对照。

### 13.3 数据治理验收

- 100% 的常驻文件有 license tag。
- 受限数据不进入公开镜像。
- 所有核心记录有来源和 snapshot date。
- 撤回、更新和 superseded accession 有不可变记录。
- coverage 报告明确说明未覆盖来源和未解析记录。

## 14. 主要风险与处理

| 风险 | 影响 | 处理 |
|---|---|---|
| TaxID 或 strain 标注缺失 | 错误合并不同菌株 | strain_unresolved 标记，不自动整合 |
| library_strategy 错误 | 组学分类错误 | title/protocol/publication 二次分类 |
| fastq_bytes 缺失 | 体积低估 | 文件级 HEAD/清单二次核验 |
| processed matrix 不一致 | 伪相关 | raw 统一重处理优先 |
| 许可不清 | 不能公开复用 | quarantine，不进入公开层 |
| 全量下载失控 | 存储和费用爆炸 | dry-run、配额、审批阈值 |
| 来源 API 限速或故障 | 下载中断 | adapter 隔离、缓存、指数退避 |
| 重复数据 | 存储浪费 | accession crossref + checksum |
| 作者撤回或版本更新 | 可追溯性受损 | append-only + tombstone |
| matched sample 稀少 | 因果解释过度 | A/B/C 分层并降低结论强度 |

## 15. 立即执行清单

1. 冻结 `scope.yaml` 和 `selection_policy.yaml`。
2. 建立 NCBI、ENA、GEO 三个第一优先级 adapter。
3. 生成全物种 ENA read_run 清单，只统计不下载。
4. 单独生成 MG1655 subset，并计算 runs、bytes 和 license 分布。
5. 建立 PRIDE、MetaboLights、Metabolomics Workbench 的最小导入路径。
6. 固定 GCF_000005845.2、iML1515、RegulonDB 和 UniProt 快照。
7. 选择 20-50 个 MG1655 assays 做真实下载与处理试点。
8. 根据试点结果修正评分阈值、存储上限和单位成本。
9. 建立公开/受限数据的物理隔离和 export policy。
10. 将下载完成定义改为“可追溯、可校验、可重处理”，而不是“文件已经存在”。

## 16. 最终建议

第一阶段不要追求“所有 E. coli raw omics 都在本地”。

可行且有科学价值的版本是：

```text
全量 metadata
  + MG1655/关键菌株选择性 raw
  + 标准化 processed
  + RegulonDB/EcoCyc/iML1515 知识约束
  + 全物种 assembly/pangenome
  + 其余 raw 按需回源
```

这套方案可以控制存储和下载时间，同时保持数据覆盖、可追溯性和后续扩展能力。
